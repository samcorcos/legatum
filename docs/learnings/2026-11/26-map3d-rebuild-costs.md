# 3D map rebuild costs and local updates

On the PR 283 map, a cold `MapScene.setView` spent about 213–233 ms sampling the terrain field and 38–47 ms creating the terrain mesh. Its unchanged-view path spent about 70–74 ms recomputing fog over the whole field. The map is 48×32 tiles, but the terrain field has hundreds of thousands of vertices, so per-vertex string-keyed bump lookups, repeated nearest-tile searches and generic normal accumulation dominated.

Dense bump bins, a three-candidate nearest-hex lookup, typed tile-centre/adjacency arrays, an unknown-region fast path, and a regular-grid normal pass reduced the measured cold build to 84–90 ms without a visible change at camera distances 3, 8 and 18. An exact precomputed noise lattice cost more to build than it saved and was removed. `forceRebuild()` must clear all scene caches for an honest cold measurement.

An identical view can return immediately. For a new fogged view, changed fog vertices and tree instance colours can be updated in place; a border-only change can replace just the border layer; a small newly explored area can update terrain vertices and normals locally. These paths measured 0.8–2.7 ms for four fog changes, 1.1–2.2 ms for one border change, and 2.4–5.9 ms for a one-tile reveal on the M3 Max shot service. A cold build on the main thread still took more than 50 ms after those paths, so the terrain build moved to a Web Worker (`map3d/fieldWorker.ts`): the previous map stays on screen until the new one is ready and stale results are dropped. The main thread now blocks about 1 ms when a rebuild starts and at most about 25 ms when the new terrain is put on screen (turn-204 strategic view, M3 Max); wall time to the new terrain is about 90–140 ms.
