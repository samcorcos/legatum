## 2026-11-22: Co-op starts the six AIs in three Alliances (`claude/review-coop-preset`)

- **Design:** an optional `GameSetup::ai_alliances` (off by default, skipped when off) signs the AI-only teams into Alliances of two when the game is built, as ordinary treaties between solo teams: they can be left or broken, upkeep applies, VP is not shared. Permanent teams were rejected: they would merge the AIs' score and victory and cannot break. The pairs come from a seeded order of the AI team ids (`rng::seeded_order`), so seat order does not matter and no hash-map order is involved.
- **No `RULES_VERSION` bump:** the field defaults off and is omitted from the JSON when off, so every old setup, save and tape parses and hashes as before, and the new data (an Alliance in `relations`) already exists in the state format. An older build given a setup that has the field would ignore it and play without the alliances; the hosted site keeps old builds per version for that reason.
- **Where it is wired:** the app's Co-op preset (hot seat and hosted rooms start in it) sets `Lobby.aiAlliances`, Game settings show AI alliances On/Off, and the hosted room carries `ai_alliances`. Solo, Teams and Free-for-all leave it off. `GameSetup::standard` leaves it off on purpose so the sim pins stay put; a test turns it on.
- **Gotcha:** `determinize.rs` rebuilds a `GameSetup` from a view for search rollouts; it keeps `ai_alliances` false, because `blank_game` would sign the pairs again over a state that already holds the real relations.
## 2026-11-22: Co-op AI alliances follow-ups
- **A rule that a loaded game must also explain has to ride in the view, not the lobby.** The Relations note reads `PlayerView.ai_alliances` (true when `GameSetup::ai_alliance_pairs()` is non-empty), so a saved game says it too. It is a view field only, skipped when false: no change to hashed state, saves or `RULES_VERSION`. Any other literal `PlayerView { .. }` (the AI fixture) needs the field.
