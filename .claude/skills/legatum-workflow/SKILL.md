# Legatum workflow

- **Worktree pool safety (2026-10-09):** `tools/ops/agent-worktree.sh` once freed slots by checking a one-shot shell PID, and its reset/clean wiped two agents' uncommitted work. Fixed: locks end only by `release` or after 12 hours, and a slot with uncommitted changes is never reset. Agents commit early (WIP commits are fine) so work never lives only in a working tree. Prefer a dedicated worktree for long tasks. `acquire <branch>` on an existing branch checks it out where it is (2026-11-08; it used to `checkout -B` it back to the base and drop its commits) and refuses if another worktree already has it checked out; only a new branch is cut from `--base`.

## How the user wants to work
- **GitHub is the source of truth, one line on `master` (user, 2026-11-21).** All work: branch from `origin/master` → push → PR into `master` → CI (`.github/workflows/ci.yml`: `gates`, `lint`, `rust-test` groups from `tools/ci/rust_test_groups.py`, `wasm`, `app-test` shards, `app-build`; branch protection requires the one aggregate check `ci-ok`; Markdown-only changes skip the builds; pushes build only on `master`; while GitHub Actions is unavailable, a passing `tools/ci/local-ci.sh` run posted as a PR comment stands in for it, see CLAUDE.md) → reviewers → merge on GitHub → `git pull` on the Mac. Nothing lands by a local `git merge` any more, so `.claude/hooks/merge-gates.sh` and `tools/ops/land.sh` only matter for the old private history. The Mac's pre-switch history is the branch `archive/mac-master-2026-11-21` and `~/LegatumData/backups/legatum-full-2026-11-21.bundle`; it shares no commits with GitHub `master`, so old work comes over as a diff onto a branch from `origin/master`. Sim results and other files GitHub doesn't hold live in `~/LegatumData/sim-results` and `~/LegatumData/private-tree`.
- **Who merges (user, 2026-11-21):** Claude merges a PR it made at the user's request once CI is green and the reviewers its paths need have passed. Never merge an outside contributor's PR without the user.
- **Number anything that needs the user's answer** (1., 2., ...) so he can reply by number (user, 2026-11-21).
- **Save compatibility (designer, 2026-10-31):** bump `crates/core/src/lib.rs::RULES_VERSION` for every rules or save-shape change. Refuse saves from other versions with the load-screen message; do not write migration or grandfathering code. Never alter existing save files on disk.
- **Three test gates (user, 2026-10-18):** a normal change runs types, unit tests, the build and a small set of core Playwright flows; the extended gate adds the full Rust workspace and wider browser tests; the release gate adds the full two-size screen tour and WebKit. The tour is split into domains that can run alone. Profiles, failure policy and measurements are in "Test gates and verify speed" below. Plan items CL23, CL24, CH25 in `docs/status/review-plan-2026-10-18.md`. The review plan is also the durable checklist for the 13 Codex code reviews: read it before starting review-derived work.
- **Thought partner, not order-taker:** give a recommendation with reasons; push back when evidence says so; say plainly when an earlier claim was wrong (and correct the docs).
- **Never idle the AI plan while waiting for a playtest (user, 2026-10-29 and 10-30: "it doesn't look like it's moved very much since last night?", then "how is this going?" after another idle day):** publishing a playtest build is not a stopping point. Start the plan's next step, behind genes and on a branch, in the same turn as the build; playtest feedback folds in when it arrives. Leave `running_now` empty overnight only if a budget cap blocks the work, and say so.
- **Skateboard delivery:** something playable early, then improve. Playtest builds are the checkpoints; the user tests specific hypotheses (e.g. "I'll play a rush").
- **Long paid runs must show interim evidence (user, 2026-10-09, during the overnight cloud league):** "no progress we can show yet? I just want to make sure we don't spend a bunch of time and money on this and then nothing works at the end of the run." Before and during any long or paid run (cloud league, evolution, big batch), define a mid-run check and its stop condition. Report held-out or human-seat numbers as they come in, and stop early if nothing transfers (see learnings 2026-10-09, validate mid-run).
- **Parallelize to the maximum, and estimate at parallel speed (user, 2026-11-21):** "you'll say things take days or weeks when you can actually parallelize it with multiple agents ... There's no way that this can take this many days." Split work behind a written contract into independent pieces and run them at once (sub-agents in worktrees, the 64-core box, the Mac, Codex lanes, Cloudflare). Give estimates in wall-clock hours at that speed and name the critical path (integration, gates and reviews, or a step only he can do). Never quote human-team days or weeks.
- **Talk to the user in plain language (user, 2026-10-09):** he replied "I'm not sure I understand" to "Gains shrink when combined. Results measured on a separate branch often don't hold up..." Explain results in concrete terms with a one-line example; skip internal shorthand (branch names, gene names, jargon) unless he asks.
- **Say "stopped" or "unused", never "idle", for the cloud box (user, 2026-10-30: "i thought you turn off the box when it's not in use so i don't pay for it, no?"):** the box stops itself after 20 idle minutes and bills only for hours worked, plus about $1.60 a day for its 600 GB disk. When it hasn't been given work, say it sat stopped with nothing queued, and that the cost is lost progress, not money.
- **Split work between Claude and Codex (since 2026-10-03, Claude Max 20x).** Claude subagents (worktree-isolated) take a fair share of implementation, especially work needing judgement, design taste or careful review. Astra/Codex takes long simulation-heavy runs and mechanical work. Keep both busy. Still prefer CPU for simulations and avoid wasteful polling (one background wait per event).
- **Branch verification:** before landing a Codex branch, the lead can run `tools/astra/verify-branch.sh <branch> [--duel] [--app] [--no-cache] [--full] [--serial]` outside the Codex sandbox (on the 64-core box: `tools/cloud/verify-remote.sh <branch> [--app] [--profile fast|extended|release] [--shards N|auto|1]`; see "Test gates and verify speed" below). It locks/reuses a verifier worktree, merges onto the current master snapshot, and records check logs and statuses under `.progress/verify/<branch>/`; `--dry-run` prints the plan. Since 2026-10-10 the independent steps run **concurrently in lanes** sized from the core count: the release-checked build then tests, the branch smoke and repin; fmt and clippy; the master baseline; and the WASM, then tsc, vitest, app build, Playwright chain. Tests run through `tools/astra/gate-tests.sh` (cargo nextest plus doctests; the same 1,651 tests, `cargo install cargo-nextest --locked`, falling back to `cargo test` without it). The branch smoke and duel use the `release-checked` binary the test build already produced, `repin.sh` reuses those artifacts (`LEGATUM_REPIN_PROFILE=release-checked`), and master's smoke and duel come from `tools/sim/cached-baseline.sh` (keyed by the sim code, so a docs or app move on master is a cache hit). Playwright runs cores/3 workers (up to 24, fewer when the machine is already loaded) with a 90 s default test timeout. **Steps the branch cannot affect are skipped and listed with the reason** in the summary: docs/skills only (merge plus syntax checks); app only (no cargo steps; the app lane turns on without `--app`); crates only (WASM, tsc and vitest for browser-facing WASM tests, but no app build or Playwright unless `crates/core/src`, `crates/wasm`, `app/`, `scenarios/` or the Cargo files changed). An unclassified path, a branch named master and `--full` skip nothing, and the release check always runs everything. Never wrap a script's inner cargo calls in `build-slot.sh` (not re-entrant). PASS results are cached by step, exact command, code tree and relevant tool versions in `~/LegatumRuns/gate-cache/` for 14 days; concurrent verifiers wait for the same step result. Use `--no-cache` for a fresh run, including the once-a-day master health gate. Release checks do not read this cache. WebKit is never run on the host.
- **Model choice for Codex (Astra queue):** only sol (gpt-6-sol, default) and luna (mechanical work). Never gpt-6-astra; the runner maps it to Sol (user, 2026-10-04). Claude subagents: Fable is allowed for now (user, 2026-11-11: "we have a lot of fable tokens right now, so let's lift this restriction for now. we can bring it back later if needed"); use it for diagnosis, audits and design research, not routine implementation. `gpt-6.1-sol` is rejected on this account. Set `model:` and `effort:` headers.
- **Never disturb a live game:** renice background work to 15 (`renice 15 -p PID`, absolute form) while the user plays, and publish a playtest to a new preview label rather than over the one he is playing.
- **Record as you go:** design decisions go to the design doc's decisions log; learnings to docs/learnings.md; rule changes to the legatum-rules reference; preferences to the legatum-design or legatum-ui skills.

- **Push back before agreeing (user, 2026-10-31):** "when i come up with an idea like this you generally agree with it, which tells me there are likely other recommendations and things that you could come up with yourself." For each of his ideas, give the strongest case against first, then the recommendation. Originate simplification and improvement proposals with evidence, including challenges to settled decisions; a standing Astra design review (`.reviews/astra-design-simplify-review.md`) feeds them.

## Model routing: the cheapest model that meets the bar (user, 2026-10-04)
- **Balance the two subscriptions (user, 2026-10-31):** "the more we can offload to chatgpt the better." While Codex has headroom against its reset:
  - **Codex:** AI audit rounds, implementation, landing prep (master merges, conflict fixes, repins), sims and analysis (Sol; Astra for the hardest work). The merge into master stays with Claude, behind the docs gate.
  - **Claude:** design calls, Chromium UI checks, the final review before merge, and talking with the user.

  The ops supervisor checks both budgets each run and says which way to lean.
The lead judges the model for every task, delivered or requested, to maximise token efficiency without losing quality. Both the Claude and Codex budgets are limited. Default routing:

| Work | Model |
|---|---|
| Design, rules and faction decisions; merge decisions; talking with the user; novel architecture (e.g. the goal-driven AI's value function); hard root-cause debugging; the ops supervisor (user asked for Opus) | Claude Opus 5.5 ($4/$20 per MTok) |
| **Default for agent work** (Sonnet 5.5, current since 2026-10; $2/$10, half Opus's price, positioned for everyday coding and agent work): implementing well-specified features and rules changes, landing agents, UI work with Playwright verification, code review, routine fixes, resuming a spec'd task | Claude Sonnet 5.5 (the Agent tool's `sonnet`) |
| **Cheap tier, plenty of credit (user 2026-10-17: "you can use haiku 5.5 and luna on codex for tasks that don't need peak intelligence and we have way more credits for that")**: log or status sweeps, file moves, scripted checks, summarising sim reports, running sims and reporting numbers, simple copy and UI tweaks with a clear spec, docs | Claude Haiku 5.5 (the Agent tool's `haiku`) or Codex Luna, or a plain script with no model |
| Implementation, AI changes, analysis | Codex Sol where the sandbox allows it (user 2026-10-23: "we have a lot of ChatGPT credits right now... sol is a good model... use your judgment"); otherwise Claude Sonnet 5.5 |
| **First choice for any well-specified task** (user 2026-10-07: plenty of ChatGPT credit, "anytime we can hand something off to luna without losing quality"): implementation with a clear spec and a measurable test, AI tuning, playtest analyses, small UI fixes, docs, scripts, running sims | Codex Luna |
| Diagnosis, valuation audits, trace reading, design research | Fable, while the 2026-11-11 lift lasts |

Patterns:
- **Sub-agents hand back every time they wait on a box job** (2026-10-23: the bisect agent sent about a dozen full "PARTIAL" reports in a row). Brief long jobs to send a one-line interim note while waiting and the full report only when done or blocked; that saves the lead's context and the user's attention.
- **A sub-agent must not start its own UI reviewer and then hand back** (2026-10-20): the strategic-supply agent did, the reviewer's result never reached anyone, and the branch sat unlanded. The lead runs the `legatum-ui-reviewer` on a finished branch, or the agent waits for its reviewer before handing back.
- **Commits in the main checkout use explicit paths** (`git commit -m … -- path`), never `-a` or `add -A`: agents may have unfinished edits there (2026-10-18, a learnings commit swept an agent's AI work onto master). Agents edit only in their own worktrees.
- **Pace the session (user 2026-10-17):** at most about 4 Claude agents at once; Opus and Sonnet agents share the session limit, which ran out once with 15 agents running. Queue the rest in `docs/status/next-tasks.md`.
- **Cheap does, better checks:** Luna or Sol implements, Sonnet verifies (tests and screenshots), and Opus only judges design-relevant results.
- **Escalate on evidence:** move up a tier when the cheaper model fails a check twice, or the work turns out to need design judgement. Move down when a tier proves reliable for a task type.
- **Scripts before models:** anything repeated (status snapshots, release checks, re-pinning) becomes a script, so no model is spent on it.
- **Learn:** the supervisor records which tier worked or failed per task type in the legatum-ops playbook, and adjusts these defaults.

## AI quality
- **Model-seat games replicate him, not play from scratch (user, 2026-11-15):** "take a game that Sam (me) played and see if we can replicate / change the outcome by making better decisions... fable should be able to play a new game (on a new map with new opponents to avoid over-fitting) and try to replicate the same level of success and make similar decisions." A seat game is briefed with his playbook (`docs/playtests/human-reasoning.md`, `legatum-coach`), on a fresh map, played every turn (the 2026-11-14 games skipped quiet turns with standing-order loops, about 22 s a turn on average, and lost cities to it), and scored against his milestone curve with Hard on the same seat and seed as control. A shortfall despite the briefing means the playbook is missing something; a match means the playbook is the spec for Hard. Findings are replayed before any Hard change.
- **Live "why did you differ from Hard" capture in his games (user idea, 2026-11-11; proposed, not decided):** "run the hard AI alongside me when I'm playing... write down what the hard AI wanted to do and why, as well as what I decided to do... if you see a material discrepancy... prompt me and say 'hard ai wanted to do x, but you chose Y, why?'... push back if needed." Lead's answer: the Hard-versus-him diff already exists after the game (the decision audit replays his tape with Hard shadowing his seat, exact), so the only new value is his reasoning caught in the moment. Recommended shape: a note hotkey that stamps turn and text into the tape, then a few deterministic, non-blocking end-of-turn questions on big category divergences (war, peace, settle, army commit, large purchase), rate-limited; no model call in the live loop. Wait for his call before building.
- **Judge AI work by his games first (user, 2026-10-31: "i just really want the AI to be better and im grasping at straws here. please help come up with a better plan"; "ok i trust your judgment").** The 2,048-game gate rates nearly every change neutral, so it can't be the only scoreboard. Score AI changes first on fixtures cut from his games (his positions, the coach's scenarios) and on the decision audit, which ranks Hard's mistakes by value lost against his own decisions. Use the gate as a regression guard. He suggested a strong player playing Hard while we log what Hard would have done instead; the audit uses him as that player, and an LLM can be plugged in later as a second one. When he asks for an open review, queue it to gpt-6-astra (`model: astra`) in the Astra queue.
- **North star (user, 2026-10-07):** keep improving the AI until Hard performs consistently at least as well as Sam did as a good human. Use the fixed-map human-seat benchmark in `docs/sim-results/hard-vs-human/README.md` before making quality claims. Run `tools/sim/hard-vs-human.sh --local --brain hard --salts 64` and the matching `hard+search` command; candidate parameter files use `--ai-params FILE`. Every run appends map win rates and city/VP milestone medians to the ledger and redraws the portrait chart. Each salt changes AI RNG only.
- **War scenarios: the campaign hill-climb (user idea, 2026-10-11).** Short wars cut from the user's playtests (18 in `scenarios/war/` after the 2026-11-07 sweep; nine when it began, each with a goal, a turn limit and his own result), played by the AI in his seat against the same opponents. Score any AI change with `tools/sim/war-scenarios.sh --brain hard --runs 64 --ai-params FILE --params-seats seat` (also `--brain hard+search`; without `--ai-params` it is the baseline): it builds `war_suite` on the box, runs on one spot server (about a minute of compute, cents), appends `docs/sim-results/hard-vs-human/war-scenarios/ledger.jsonl` and redraws the portrait chart. Runs are seeded by index, so compare two reports run by run with `python3 tools/sim/war-scenarios-report.py --compare BASE.json CAND.json`. The suite score is mean goal success; "human parity" counts scenarios met in half the runs no slower than the user. Rebuild the start states with `tools/scenarios/extract-war-states.sh DIR` then `legatum-sim war-build --states DIR` (replays each save on its own engine, hash-checked every turn). One case has the AI as attacker (`war-golden-horde-thin`, from the 8.9.2 Mongol assault; the 2,235-Gold original and the mirror `war-golden-horde-hold` were deleted in the 2026-11-07 sweep): `tools/sim/war-scenarios.sh --check` is the attack regression check (Hard, 64 runs, exit 1 under 60%; since 2026-10-30 the defenders play `tools/sim/attack-check-defenders.json`, door defense off, through `war_suite --opponent-params`: with the door on every attack case read 0%; baseline 89%). Do not edit that script while a run is in progress. Scenarios whose attacker the Hard AI cannot play (a bomb-then-capture operation it never runs) carry a script: the designer's recorded orders for his seat, `scenarios/war/scripts/<id>.orders.json`, replayed by `war_suite` and `war_trace` through `crates/sim/examples/war_script` (`war-german-air-early`, `-t219`); the report also counts the other side's losses (*Enemy units lost*, `enemy_units_lost_by`), the exchange ratio. Details: `docs/sim-results/hard-vs-human/war-scenarios/README.md`.
- **Scenario gate: the sensitive A/B for gene changes (2026-11-09).** `tools/sim/scenario-gate.sh CANDIDATE.json` plays every Lab card and war scenario per arm on shared dice seeds (default: the 15 held-out cards, 480 runs per arm, local; about 4 minutes on a quiet 16-core Mac, about 27 minutes when other sims load it; 128 runs on all 44 cards for the siege-off calibration) and prints per-card deltas, a pooled delta in card SDs with a 95% interval and a noninferiority verdict (exit 1 on FAIL); `--mode rivals` for rivals-only, `--him designer` puts the imitation seat (`legatum_ai::designer`, measurement only: Hard plus his Walls-first and no-routine-purchase habits; it predicts 26% of his decisions on the held-out tape against Hard's 23%, and Hard in the seat does about as well against it as against Hard, so it is about as hard as Hard, not as hard as him, and a weak proxy for now) in his empire (the opponent column), `--aa` measures the noise floor. It resolves changes the human-seat benchmark can't (siege-stance genes off: −0.042 SD [−0.060, −0.025], −2.5 pp objectives met; on human-seat +1.46 [−0.05, +2.98]). Tune and read cards only on `--set train`; accept on `--set held_out` (the default), fixed in `docs/sim-results/scenario-gate/split.json` and never retuned on. Card SDs are not win rates: keep the full-game benchmark weekly as the guardrail. Details and calibration: `docs/sim-results/scenario-gate/README.md`. Not a merge gate.
- **Card loop: where Hard first departs from a winning line (2026-11-09).** `tools/sim/card-loop.sh` (local; `--score-only` about 2 minutes, a full run about 1.5 hours under load) scores Hard on every Lab card, searches each failing training card of the gate's split (held-out cards are only scored), and writes one task per first divergence to `docs/sim-results/ai-quality/card-loop-queue/tasks/` for the lead to triage, never to the astra queue. Details: `tools/sim/card-loop-README.md`.
- **The milestone climb: gene search against his own numbers, no LLM in the loop (user idea, 2026-10-18).** `tools/evolve/milestone_climb.py --genes tools/evolve/genesets/X.json --maps MAP --run-id ID` runs CMA-ES on the human milestone suite (`docs/sim-results/ai-quality/milestones/`: his cities, eliminations, Gold and VP by turn from his saves, scored as min(AI/his, 1)). Each generation is one batch of `milestone_suite` with the population, the CMA mean and the built-in AI on the same fresh salts. `--backend auto` uses the box's idle filler and falls back to spot. Held-out salts and maps are checked every few generations, and `--resume RUN_DIR` continues a run. A generation of about 2,700 games is about 15 seconds on one spot server: the launch minute costs more than the games, and the shared spot quota (448 vCPUs) is the real limit. **Gate every result on full games before believing it**: the first runs gained +0.05 to +0.11 of milestone score that held on new games, and lost 4.9 pp of full-game wins (see `docs/sim-results/ai-quality/optimization-program.md`). Plan and roadmap in that file.
- **The benchmark's rivals are plain Hard (2026-10-28), like the app's default lobby:** `hard_vs_human` ignores the maps' `search: true` unless `--rival-search` (or an arm's `"rival_search": true`) is given, because Search rivals never bomb. Control on 8.9.14: 16.2% (331 of 2,048), against 36.4% with Search rivals. Ledger rows and `docs/sim-results/ai-war/baseline.md` W0.4 and earlier were measured against Search rivals, so never compare them with new runs. Details: baseline.md W2.0.
- **Seat-split rule (user, 2026-10-10):** measure AI changes with `--seat-brain` and `--opponent-brain` on the same fixed maps and salts against baseline params in one binary. Seat-only candidate minus baseline is the north-star measure of the candidate's skill in Sam's seat. Opponent-only measures whether the changed rivals became harder (lower seat wins is better). Report all-seats as context, not as the decision criterion. Gate every behavior difference behind genes so baseline and candidate differ only by params; use paired outcomes to judge noise.

- **Judge changes to early exploration or opening order in a league, not on the fixed maps (2026-10-18).** Every salt of a `hard_vs_human` map shares one set of combat, movement and barbarian dice, so any behaviour change flips whole maps (single maps swung 60 wins, and the same gene read -0.4, -10.7, -5.4 and -9.9 pp at four weights) and the printed salt-bootstrap interval says nothing about that. Either run it with `LEGATUM_HVH_RESEED_DICE=1` (each salt plays its own dice; control 26.9% against 35.2% with the fixed dice) or, better, a league of fresh seeds: `tools/cloud/run-batch.sh --ai-params CANDIDATE.json --opponent-params CONTROL.json -- --players 8 --difficulty hard --games 9000 --seed 7100001 --label NAME` puts the candidate in half the seats and the control (an empty `{"schema":1,"name":"builtin"}`) in the rest; read `summary.by_brain` (wins per group; SE 0.5 points at 9,000 games; run an empty candidate too, the seat assignment alone was worth +1.2 on one seed set and 0 on another). It takes about 12 minutes and $0.15 on one spot server. Check 4 and 2 players and a held-out seed block (9100001+) before turning a gene on.

## Pipeline patterns that worked
- Every game-rule or save-shape change increments `crates/core/src/lib.rs::RULES_VERSION`; a current save round-trip and a different-version refusal test guard the boundary.
- **Cloud AI parameter files:** pass a local file to `tools/cloud/run-batch.sh` before `--` with `--ai-params <file>`. The launcher uploads it to the batch bucket and rewrites the sim argument to its server-side copy; `--dry-run` prints the S3 key and each remote command without making AWS calls.
- Determinism merge hotspots: resolve conflicts in `crates/sim/tests/fixtures/` (including its README) and `crates/sim/tests/pins.json` by taking either side, then run `tools/sim/repin.sh` on the merged code. It regenerates mixed tapes, rehashes fixed-order tapes, recomputes runner pins and runs release pin/determinism tests. Review the diff and explain intentional changes before committing; do not hand-edit hashes.
- AI-quality merge hotspots (2026-11-03): two AI branches always conflict in `docs/sim-results/ai-quality/chart.html` (generated) and the appended `plans/ai-war-progress.txt` lines. Keep both progress lines; take either chart and regenerate it with `python3 tools/ai-quality/chart.py` from the merged `ledger.jsonl` (which merges cleanly).
- Hold queue: stage tasks in `.progress/astra-queue/hold/` and release when their prerequisites merge (shared files mean sequential, not parallel).
- **Keeping docs and skills current, automatically (user, 2026-10-10: "keep our documentation and skills up-to-date without me needing to ask"):**
  - **Real-time:** the Stop hook `.claude/hooks/docs-check.sh` blocks once after the user's message reads like a decision, preference, rejection or correction when no skill, memory, CLAUDE.md or human-reasoning file changed while answering it. `learnings-check.sh` covers code changes and learnings.
  - **Periodic:** the hourly app scheduled supervisor (`legatum-ai-supervisor`) runs a docs audit. It reads user messages since the last audit from the session transcripts, checks each decision against the right home, patches gaps, and keeps state in `.progress/doc-audit/`.
- **Budgets are for prioritisation, not slowing down (user, 2026-10-10):** "if there are tasks that require lots of tokens and we are low on token budget prioritize things that use CPU. If we are approaching our AWS budget, use more local CPU because it's free." Never idle the pipeline to save budget; shift the mix instead.
- **The tracker (`docs/status/tracker.md`):** when the lead promises the user something (a deliverable, a fix, a time), it goes in the tracker in the same turn, along with anything waiting on the user and every bug report. The supervisor flags overdue items. The era proposal promised for the evening of 2026-10-09 slipped silently, which is why this exists.
- **Operational lessons (2026-10-09/10):**
  - **Measure AI changes twice.** Run the human-seat benchmark seat-only (the candidate only in the human's seat) and opponent-only. All-seat runs penalise changes that make every AI better.
  - **Cargo EPERM:** if `cargo` from the lead's shell fails with EPERM writing `.d` files in a repo `target/`, build with `CARGO_TARGET_DIR` in the scratchpad. A stale `app/src/wasm-pkg` then causes false WASM test failures, so rebuild WASM before trusting them.
  - **Running Codex tasks never see edits to their task file.** To change one that started minutes ago, kill its PID (`.reviews/astra-<name>.md.pid`) and requeue it as `<name>-v2`.
  - **Queue order follows file mtime.** Editing a pending task file sends it to the back; `touch -t` an old timestamp to put it first.
  - **Stale builds:** before trusting e2e results in any checkout, rebuild the WASM package and the e2e web build (`LEGATUM_RELAY_URL=http://127.0.0.1:8787 scripts/build-web.sh`). The e2e fixture serves `app/dist` statically, so a stale one tests an old UI. The 2026-10-10 art audit saw 6 "failures" that came from Oct 7 builds in the main checkout.
  - **Find finished work in `.progress/astra.log`.** Before saying something is still running, check there for finished tasks. Build the landing list from that log, never from memory.
  - **The app scheduled supervisor stalls** whenever a run waits on a permission prompt. The user must approve it once, ideally "always allow".
- **Two-player online game (2026-11-22; LAN mode and `legatum-server` are gone):** both players open the web build, Multiplayer. The host picks Host Game (the game runs in that tab, which must stay open); the other picks Join Game and joins from the list. Both need the same build. ## Test gates and verify speed (D13, 2026-10-18)

Three profiles, one flag: `tools/cloud/verify-remote.sh <branch> --profile fast|extended|release` (and `tools/astra/verify-branch.sh --profile`). Without a flag a change that touches no Rust runs **fast**, anything else **extended**; **release** is always explicit.

| Profile | Rust | Playwright | When |
| --- | --- | --- | --- |
| fast | fmt, clippy, build, repin, smoke and every test except the long ones in `tools/astra/extended-rust-tests.txt` | smoke set: `game`, `turn-flow`, `research-click`, `production-picker`, `exit-to-title` | app-only, docs and tool branches; every Codex/Claude branch before landing |
| extended | the whole workspace (nothing deleted) | every `e2e/*.spec.ts`, but not the screen tour | any branch that touches `crates/`, `scenarios/`, `.config/` or the Cargo files (the default for them) |
| release | as extended | everything including the two-size tour (`e2e/tour/*`), plus WebKit (`--webkit`; `tools/release/check.sh` runs it natively on the box) | playtest builds, UI-reviewer runs, `master` health |

- **Failure policy.** Assertion, timeout and unclassified failures are never rerun: they fail the gate. A Playwright run whose failures are *all* browser transport errors (`net::ERR_NETWORK_CHANGED`, a closed browser; classified by `tools/ops/pw-summary.py`) reruns only the failed tests once (`--last-failed`); the summary shows the first run, the rerun and the error classes. A branch that fails fast is not retried at extended; fix it. If fast passes and extended fails, the failure belongs to the branch (the profile only adds tests), not to flakiness, until a rerun proves otherwise.
- **The tour is split by domain:** `app/e2e/tour/{title-lobby,turn-one,diplomacy-war,combat,research-unlocks,victory-race,factions,yam-relay,post-game}.spec.ts` share `helpers.ts`. - **Why the Rust test step took 5 minutes:** one test (`opening_league_twenty_standard_games...`, 280 s on a single thread) was the whole critical path of 570 s of test work. It now plays its 20 games side by side, nextest starts it first (`.config/nextest.toml`), and fast skips it. Re-measure with `python3 tools/ops/rust-test-durations.py .progress/verify-remote/*/steps/test.log`.
- **Artifact steps never hit the gate cache:** `app-wasm` and `app-build` produce files in the worktree, so a PASS record from another slot must not skip them (CL6). The WASM build has its own exact-input cache (key narrowed to the crates the WASM actually compiles) that restores the package and hash-checks it against its manifest.
- **Playwright workers.** A box job's workers follow its core budget (`tools/cloud/box/budget.sh`); the 2026-10-18 sweep (`docs/ops/test-gate-timings.md`) found Chromium wall time flat from 12 to 48 workers on a busy box and failures growing with the count, so more workers than cores buy nothing. - **Sharding one verify (`--shards N|auto|1`):** a main job (Rust, WASM, tsc, vitest) plus N Playwright shard jobs, merged into one summary. `auto` shards only with 3+ free slots and no queue. Sharding does not create CPU: on a saturated box the shards queue like any job.
