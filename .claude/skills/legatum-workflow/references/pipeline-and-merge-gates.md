# Workflow: pipeline patterns, merge gates and playtest builds

Merge hotspots, docs automation, the tracker, sim policy per change, merge order, the static gates (hygiene, public claims, engine invariants, art, scenario) and the old marker files, playtest build rules, performance and worktree policy. Mac and Tauri steps are historical since the game went web-only (2026-11-22).

Moved verbatim from SKILL.md on 2026-11-22 (original order kept). The current rules are in SKILL.md; where this file disagrees with SKILL.md, SKILL.md wins.

## Pipeline patterns that worked
- Every game-rule or save-shape change increments `crates/core/src/lib.rs::RULES_VERSION`; a current save round-trip and a different-version refusal test guard the boundary.
- **Cloud AI parameter files:** pass a local file to `tools/cloud/run-batch.sh` before `--` with `--ai-params <file>`. The launcher uploads it to the batch bucket and rewrites the sim argument to its server-side copy; `--dry-run` prints the S3 key and each remote command without making AWS calls.
- Determinism merge hotspots: resolve conflicts in `crates/sim/tests/fixtures/` (including its README) and `crates/sim/tests/pins.json` by taking either side, then run `tools/sim/repin.sh` on the merged code. It regenerates mixed tapes, rehashes fixed-order tapes, recomputes runner pins and runs release pin/determinism tests. Review the diff and explain intentional changes before committing; do not hand-edit hashes.
- AI-quality merge hotspots (2026-11-03): two AI branches always conflict in `docs/sim-results/ai-quality/chart.html` (generated) and the appended `plans/ai-war-progress.txt` lines. Keep both progress lines; take either chart and regenerate it with `python3 tools/ai-quality/chart.py` from the merged `ledger.jsonl` (which merges cleanly).
- Hold queue: stage tasks in `.progress/astra-queue/hold/` and release when their prerequisites merge (shared files mean sequential, not parallel).
- **Keeping docs and skills current, automatically (user, 2026-10-10: "keep our documentation and skills up-to-date without me needing to ask"):**
  - **Real-time:** the Stop hook `.claude/hooks/docs-check.sh` blocks once after the user's message reads like a decision, preference, rejection or correction when no skill, memory, CLAUDE.md or human-reasoning file changed while answering it. `learnings-check.sh` covers code changes and learnings.
  - **Periodic:** the hourly app scheduled supervisor (`legatum-ai-supervisor`) runs a docs audit. It reads user messages since the last audit from the session transcripts, checks each decision against the right home, patches gaps, and keeps state in `.progress/doc-audit/`.
- **Budgets are for prioritisation, not slowing down (user, 2026-10-10):** "if there are tasks that require lots of tokens and we are low on token budget prioritize things that use CPU. If we are approaching our AWS budget, use more local CPU because it's free." Never idle the pipeline to save budget; shift the mix instead.
- **The tracker (`docs/status/tracker.md`):** when the lead promises the user something (a deliverable, a fix, a time), it goes in the tracker in the same turn, along with anything waiting on the user and every bug report. The supervisor flags overdue items. The era proposal promised for the evening of 2026-10-09 slipped silently, which is why this exists.
- **Operational lessons (2026-10-09/10):**
  - **Measure AI changes twice.** Run the human-seat benchmark seat-only (the candidate only in the human's seat) and opponent-only. All-seat runs penalise changes that make every AI better.
  - **Cargo EPERM:** if `cargo` from the lead's shell fails with EPERM writing `.d` files in a repo `target/`, build with `CARGO_TARGET_DIR` in the scratchpad. A stale `app/src/wasm-pkg` then causes false WASM test failures, so rebuild WASM before trusting them.
  - **Running Codex tasks never see edits to their task file.** To change one that started minutes ago, kill its PID (`.reviews/astra-<name>.md.pid`) and requeue it as `<name>-v2`.
  - **Queue order follows file mtime.** Editing a pending task file sends it to the back; `touch -t` an old timestamp to put it first.
  - **Stale builds:** before trusting e2e results in any checkout, rebuild the WASM package and the e2e web build (`LEGATUM_RELAY_URL=http://127.0.0.1:8787 scripts/build-web.sh`). The e2e fixture serves `app/dist` statically, so a stale one tests an old UI. The 2026-10-10 art audit saw 6 "failures" that came from Oct 7 builds in the main checkout.
  - **Find finished work in `.progress/astra.log`.** Before saying something is still running, check there for finished tasks. Build the landing list from that log, never from memory.
  - **The app scheduled supervisor stalls** whenever a run waits on a permission prompt. The user must approve it once, ideally "always allow".
- **Two-player online game (2026-11-22; LAN mode and `legatum-server` are gone):** both players open the web build, Multiplayer. The host picks Host Game (the game runs in that tab, which must stay open); the other picks Join Game and joins from the list. Both need the same build. Local testing: `(cd infra/relay && npm run dev)` and a build from `LEGATUM_RELAY_URL=http://127.0.0.1:8787 scripts/build-web.sh`.
- Chaining: a script releases the next task when the previous one exits 0, and each task merges the previous branch first. Review the final branch once. Caveat: re-measure combined balance at the end.
- Every Astra task asks for intermediate commits (model-capacity crashes lost 7 hours once).
- **Sims use Standard only.** Never pass a speed flag or run speed cohorts.
- **Sims per change: correctness and smoke only; balance after integration** (user, 2026-10-04: "a waste of time to run all these simulations per-change when the combined ruleset will be so different").
  - Per branch: determinism and pin tests, plus a 50-game smoke cohort at Standard. It's a **functional check only**: no errors or stalls, every game ends normally, and second-city-never at 20% or less. **Faction win rates don't gate landings while the AI is weak** (user, 2026-10-04: "balancing doesn't mean very much because it's the blind leading the blind"). Report the spread for information.
  - Tuning tasks probe only their own target metric (e.g. first-Settler turn), with no full balance cohorts.
  - **No balance simulations at all for now** (user, 2026-10-04: "don't even bother with simulations for balancing, just for functionality. We can reintroduce them later when the AI has an IQ over 70"). No 400-game cohorts, no v6 runs, no faction win-rate probes, no integration baselines. Sims are only for functionality: crashes, stalls, determinism, whether the AI uses a mechanic, self-sabotage detectors, and opening pacing as a game-feel check. Balance returns after the goal-driven AI, more user playtesting, and the Laya and LLM work.
  - Per branch, run scenarios only as probes when they are the target metric; don't commit re-recorded scenario baselines (they conflict across branches, and `tools/release/check.sh` re-records all of them for each release).
  - Checks run once per task, at the end (`cargo test --workspace --profile release-checked` keeps overflow checks and debug assertions on in an optimized build). After merging master, a task re-runs only the determinism and pin tests: the landing re-runs every check on the merged code. The runner's write-task suffix says this; keep task prompts consistent with it.
  - When master moves during a landing with docs or ops changes only (nothing in crates/, app/ or scenarios/), merge master into the landing HEAD and fast-forward. Don't redo the merge or the checks.
  - A Sonnet landing agent merges branches one at a time, or in batches when they don't conflict, in the persistent `.claude/worktrees/landing`.
- Before merging: trial merge (`git merge-tree --write-tree`), then `cargo check` with the exit code checked, determinism tests, and the full release check script for anything shipped.
- The user prefers a playable build early over waiting for every check (2026-10-03): once Rust tests pass on the merged code, publish the preview (`scripts/deploy-preview.sh playtest-N`) while the full release check finishes in the background; fix anything it finds as playtest-N-1 between games. Set a cutoff and move late branches to the next playtest rather than holding the build.
- **Playtest builds: ship the working one, review after (user, 2026-11-11):** "Ship the one that works and then do UI review afterwards with a second follow up build. And only do it if you think that there's a reason to do it. Sometimes these builds don't touch a lot of UI and likely won't need to have a UI review." Cut and install the build as soon as the code passes verify (from the branch if master's gates aren't done), tell him the known warts, then run the UI reviewer only when the build changes enough UI to warrant it (the lead's call) and ship its fixes as an N.1 build. Docs review, gate check and the master merge follow in the background; the master merge gates are unchanged.
- UI gate: run the `legatum-ui-reviewer` agent before merging UI branches to master (for playtest builds see the line above). It reviews screenshots from `app/e2e/tour/*.spec.ts` (the screen tour, split into domains) at 1000x600 and 1440x900 against the legatum-ui skill. The user asked for this on 2026-10-03 after the tech-panel regression.
- **Merge gates (superseded in part 2026-11-22: reviewers no longer write `.progress/*-review/*.ok` markers, the `.claude/hooks/merge-gates.sh` hook, its test and `tools/gates/markers.py` are deleted, and `LEGATUM_GATE_BYPASS` no longer exists; each required reviewer posts a PR comment naming the reviewer and the head SHA, and `tools/gates/check.py <branch> --base origin/master --pr-comments <file>` checks them. The marker and hook text below is history, the static checks (hygiene, public claims, engine invariants, art, scenario) still apply) (user, 2026-11-07; since 2026-11-21 the landing step is merging the PR on GitHub, not `git merge` in the main checkout: "make sure the docs are always up to date going forward after each round"; and the same day: static reviewers only, "it doesn't require running a bunch of simulations").** Landing order: green verify → `tools/gates/check.py <branch> --base origin/master` (fix every static finding on the branch; CI's `gates` job runs the same checks with `--checks-only --skip art`, but only the local run sees the reviewer markers) → `legatum-ui-reviewer` if it says `ui review` → `legatum-art-reviewer` if it says `art review` (art, or code art depends on) → `legatum-plain-language-reviewer` if it says `plain review` (apply its rewrites) → `legatum-docs-reviewer` last (its truth pass covers changed player text) → merge the PR on GitHub (the reviewer markers are a lead-side step: nothing on GitHub reads them). The PreToolUse hook `.claude/hooks/merge-gates.sh` still runs the same checks on a local `git merge <branch>` into master (old private history only) and blocks until they pass:
  - **hygiene** (every branch, under a second): secrets (also gitleaks), personal data in files the public export publishes (generic patterns from `tools/release/scrub-patterns.txt`, the EXCLUDE list from `tools/release/export-public.sh`, plus the owner's untracked `.private/scrub-patterns.txt` when it exists; a value to hide is never written in a tracked file, `tools/release/test-scrub.sh` checks the tree), emails, `*.legatum` saves outside test fixtures, binaries over 2 MB outside the art folders (`app/src/assets`, `app/public`, `docs/design`, `docs/media`), `*.backup`/`.bak`/`.orig`, commented-out code, `// legacy`/`// old:` markers, edits to committed migrations;
  - **public claims** (every branch, under a second; 2026-11-21, after the README went public with nine peoples, seven eras and 35 technologies against eleven, nine and 45 in code): `tools/gates/public-claims.py` fails when the README's peoples count or names, era count or technology count disagree with `Faction::ALL`, `eras.rs` and `app/src/data.ts`. The claims a regex cannot check (levels, player counts, victory rules, platforms, the AI's scope) are a mandatory step of the docs reviewer on every branch, and it refuses its marker while one is stale. Keep the README's `<!-- peoples-count -->` and `<!-- eras-count -->` markers.
  - **Public copy decisions (owner, 2026-11-21):** "Legatum" is the final name (no "working title"); the licence stays MIT plus CC BY 4.0; public copy says plainly that the project is built largely with AI coding agents and that all the art is AI-generated (never "painted" or "hand-made"); anyone may open a pull request, CI is their bar, and the owner alone decides what merges and runs the AI review gates himself; the security contact is GitHub private vulnerability reporting; the working docs (design reasoning, learnings, plans) stay public.
  - **engine invariants** (`crates/core`, `crates/ai` outside tests, about 1 s): floats, `HashMap`/`HashSet` (random iteration order), unseeded RNG, wall-clock time, rendering crates, a `GameState`/`Player`/`Unit`/`City` change without a `RULES_VERSION` bump, `.current.` fixtures whose `save_version` lags (`tools/sim/refresh-save-version-fixtures.py OLD NEW`);
  - **art** (asset images or `tools/art` changed, about 30 s, cached per art tree): `tools/art/distinctness.py --render --check` on the branch's art;
  - **scenario** (a branch whose only code is `scenarios/lab/*.json`, plus docs; seconds): replaces the docs review and the extended verify with `tools/gates/scenario.py`: the state loads on master's engine (`legatum-sim scenario-check`: hash, legal position, objective), `save_version` is master's `RULES_VERSION`, the baseline `.json` and `.md` exist, and the copy lint passes on the briefing and card text (the branch's scenario text is not read by the docs reviewer). Any code in the branch brings back the full flow;
  - **markers:** code → `.progress/docs-review/<branch-with-slashes-as-dashes>.ok` (tip SHA first; later doc- or test-only commits keep it valid); player text (`data.ts`, `factionSheets.ts`, the Guide, `*Text.ts`, `*Lore.ts`, notices, reports, scenario briefings, and any `app/src` source line that adds a sentence) → `.progress/plain-review/<branch>.ok` from `legatum-plain-language-reviewer` (user, 2026-11-21: "have a reviewer going forward on PRs that checks for plain, simple, understandable language"); UI (`app/src/**/*.tsx`, `*.css`, `app/src/map/`, assets) → `.progress/ui-review/<branch>.ok` from the UI reviewer (ship or ship with known issues); art (assets, wonders, terrain) or the code art depends on (unit, building, faction and era names and kinds in `data.rs`/`eras.rs`, art wiring such as `unitArt.ts`, `unlockArt.ts`; `ART_IMPACT` in `tools/gates/check.py`) → `.progress/art-review/<branch>.ok` from `legatum-art-reviewer` (user, 2026-11-22: review changed art, and catch art that should have changed but didn't). Doc- and test-only branches need no review.
  A line that is right as written takes `// gate-allow: <reason>` (or `#`) on it or the line above; the reason must hold up, and the ops supervisor audits new ones. Emergencies only: `LEGATUM_GATE_BYPASS="<reason>" git merge ...` skips every gate, logged to `.progress/merge-gates/bypass.log`; tell the lead. Run the docs reviewer last, after any fix to a red verify or a static finding, so the marker names the tip that merges. It reports stale player text and copy rewrites instead of fixing code: apply those, then re-run it. Test the gates with `.claude/hooks/test-merge-gates.sh` (81 cases). In the cloud PR flow (GitHub merges don't fire the hook), run `tools/gates/check.py <branch>` and each reviewer it names yourself and post the verdicts on the PR before merging.
- **Playtest builds are fast first (user, 2026-11-15: "i trust your judgment. i just dont like waiting so long before i can do play tests").** Three rules from 8.9.44 on. (1) Build with the thin profile: export `LEGATUM_PLAYTEST_PROFILE=1 CARGO_PROFILE_RELEASE_LTO=thin CARGO_PROFILE_RELEASE_CODEGEN_UNITS=16` before `scripts/deploy-preview.sh` (about 4 minutes against 10; AI turns 8 to 12% slower, identical results; `docs/sim-results/perf/playtest-build-profile-1115.md`). Fat LTO stays for the production site and AI speed measurements. (2) Start the build at the same time as verify, and publish only if verify exits 0 with a fresh `status.tsv`. (3) An agent's last check is `tools/astra/verify-branch.sh` on its branch cut from the playtest line's tip, not its own run of the suite, so the lead's verify is a cache hit. Verify itself is not cut: it took 11 minutes on 8.9.43 and is the guard against a broken rule or save.
- Playtest build (web only since 2026-11-22, when the user dropped the desktop app): `tools/release/check.sh <worktree> <log> "Playtest N"` (builds the sim, re-records every scenario baseline, then fmt, clippy, tests, WASM, tsc, vitest, app build, Playwright), then `LEGATUM_BUILD_LABEL="Playtest N" scripts/deploy-preview.sh playtest-n` publishes it at `https://playtest-n.legatum-game.pages.dev` (needs the Cloudflare token or a logged-in wrangler; the label shows on the title screen). Tag the commit `playtest-N` and send him the link. Then the UI reviewer if the build changed enough UI. His autosave lives in the browser per site, so a new preview address starts without it: tell him to use Save to file before switching if he is mid-game. A deploy to the same address keeps the earlier builds' files (`LEGATUM_CARRY_ASSETS_FROM`, set by `deploy-preview.sh` and the production workflow; set it by hand for any other production deploy), so his open game keeps its art; without it every picture changed since his tab loaded goes blank (2026-11-22).
- **The public export brings back left-out files that exported code names (2026-11-21, `tools/release/export-public.sh`, `tools/release/referenced-excluded.py`).** An `include_str!` fixture, a default `--ai-params` path or a file a test opens is copied in even when EXCLUDE or `runtime-assets.py` dropped it, unless it is over 10 MB or matches the personal-data pattern (those print a warning and stay out). `runtime-assets.py` also keeps every file directly in an asset folder that a test names. CI installs Playwright's Chromium (`.github/workflows/ci.yml`) because the art render tests need it. A new fixture is therefore published automatically; keep personal data out of it.

- **LLM reviews double as QA:** every LLM review of game state (decision points, audits, critic) also reports bugs and impossible states, rule inconsistencies, and design flags, in a separate findings log. Triage it: fix bugs before training on affected data, and send design flags to the user.

- **Scenarios:** stored in `scenarios/*.json`. Get the AI baseline with `legatum-sim scenario <file> --runs 50 --difficulty hard [--record]`. The user's runs are browser downloads (one file per run, `<id>-<UTC start time>.json`, downloaded when the run ends, again with feedback, and as `abandoned: true` when he leaves part-way); he sends them over, or the R2 upload collects them once it lands. Compare them with `python3 tools/scenarios/compare.py <run>`. Write predictions before measuring. A position cut before the current `RULES_VERSION` can be stale: `scenario-cut` repairs old saves on the way in, and `legatum-sim scenario-reveal-migrate scenarios/lab/*.json scenarios/war/*.json` repaired the rules-25 reveal change (2026-11-08; it clears changed baselines, so re-record them with `--record` and `tools/sim/war-scenarios.sh --brain hard --runs 50`).

- **Fast sim builds** (2026-10-06): `cargo build --profile sim` (fat LTO, ~10% faster than `--release`) or `tools/sim/build-pgo.sh` (LTO + PGO, another 3–8%; rebuild after big engine or AI changes). Measure speed with `sim_bench` (docs/sim-results/perf/README.md).
- **Re-gate merged crate changes before fast-forwarding master** (lead, 2026-10-06), even when both sides were gated: a landing once fast-forwarded an un-gated merge with another branch's crates changes. Any change to view fields also runs the WASM build and the full vitest suite (browser-facing types must match the view).
- **Performance** (2026-10-03, user):
  - `legatum-ops-supervisor` (`.claude/agents/`) watches the fleet, machines and budgets: duplicate work, oversubscription, missed parallelism, stale worktrees. `legatum-perf-supervisor` (user, 2026-11-21: "everything just get better and faster over time, not bloat and complexity") measures master nightly with `tools/perf/lean_check.py` (speed, AI turn time, sizes, CI time, code and dependency counts, instruction weight) and opens one behaviour-identical speedup or deletion PR a week. It runs as a scheduled task in a Claude cloud container, never on the Mac or the AWS box. It also reads real players' turn-time telemetry from the uploaded games (frame time once recorded) (R2, read API) and adds telemetry wherever something looks off and the records can't say why (user, 2026-11-22).
  - sccache is the global rustc wrapper (`~/.cargo/config.toml`), shared by all worktrees.
  - Measure master baselines only with `tools/sim/cached-baseline.sh -- <sim args>`. It's keyed by the sim code's content, so docs-only commits reuse it. Never re-measure master inside an agent.
  - Run every sim cohort through `tools/sim/slot.sh -- <cmd>` (a machine-wide thread cap, default 12) with `--threads` 6 or less. Sims are CPU-bound, so queueing costs no throughput and frees cores for builds and tests.
  - Codex tasks and other background work wrap Cargo builds, tests and clippy in `tools/sim/build-slot.sh -- <cargo command>` (a machine-wide FIFO cap on heavy builds, default 3). The landing agent and `tools/release/check.sh` are the critical path and don't queue in it.
  - `~/.cargo/config.toml` caps `jobs = 8` and `RUST_TEST_THREADS = 4` per build.
  - **Size local heavy jobs to the free cores, not a fixed cap (user, 2026-11-15):** "lift the cap please. can you do it dynamically instead of a cap? you can make sure, for example that at least 2 cores are open instead of capping at 6." The old rule of 6 threads while he plays (4 per agent) is gone. Every build, verify, repin and sim on the Mac takes its thread count from `tools/ops/free-threads.sh` (cores, less the one-minute load, less 2 kept open; never under 2; `free-threads.sh N` gives each of N jobs started together its share; on the playtest line until that lands on master), e.g. `CARGO_BUILD_JOBS=$(tools/ops/free-threads.sh)`. `verify-branch.sh` ignores `CARGO_BUILD_JOBS`: pass `LEGATUM_VERIFY_JOBS` and `LEGATUM_VERIFY_TEST_THREADS`. Agent briefs name the script instead of a number.
  - **AI fixes ship before they are measured, and every finished fix gets its own build (user, 2026-11-15: "yes to 1 and one build per fix, measure 2"):** he asked why fix builds took 1.5 hours. A fix is cut into a playtest build as soon as its tests and verify pass; the before/after census, scenario guards and ledger row run afterwards, and a fix whose numbers are bad is backed out in a follow-up build. Never hold a finished fix for a second one. Agent briefs say: commit the fix with its tests and report at once, then measure. Pending his ruling after measurement: a faster playtest build profile (parallel codegen, light LTO) in place of fat LTO on one codegen unit.
  - sccache shares registry dependencies but not our own crates across worktrees (cargo's `-C metadata` includes the path), so expect a hit rate of about 35–40%.
  - zsh gotcha: in `"$sha:crates"`, zsh applies the `:c` modifier. Use bash or `${sha}:crates`.

- **Worktrees: lanes, not one per task** (user, 2026-10-04). Each Codex worker reuses its own persistent worktree (`.claude/worktrees/lane-<k>`, started with `tools/astra/runner.sh queue <k>`), so builds stay incremental. Claude agents should also reuse an idle warm worktree when one exists, rather than get a new one. One agent per worktree at a time.
- **Claude worktree pool** (user, 2026-10-07): Claude agents acquire a warm worktree with `tools/ops/agent-worktree.sh acquire <branch>` (optional `--base master`) and release it with `tools/ops/agent-worktree.sh release <path>` when done; do not use `git worktree add` for agent tasks. If it fails with "'master' is already used by worktree", pass `--base $(git rev-parse master)` (a detached base). The ops supervisor runs `tools/ops/stale-worktrees.sh` in dry-run mode each run, then `--apply` for clean merged worktrees that the report marks reclaimable.
